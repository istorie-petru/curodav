# Feature: Tasks

**Code:** `desktop/src/features/tasks/` (`widgets.py`, `table_view.py`, `timeline_view.py`, `subtask_tree.py`, `tag_autocomplete.py`)
**Status:** Implemented, with a queued UX rework — see [`../plans/tasks-ux-rework.md`](../plans/tasks-ux-rework.md) (deleted 2026-08-11, superseded by the webapp rework)

## Views

- **Table view (default)** (`table_view.py`, reworked 2026-07-19 — see below) — `QTableView` with dropdown-in-place editors for status/priority/project rendered as colored pills (not raw text), a Smart-filter chip bar up top, user-configurable+persisted column visibility/order (right-click a header, or drag one directly), plain-text edit for the rest. Click a cell to edit inline. Right-click a row for duplicate/delete; right-click a header for column show/hide/reorder. Column sorting by header click. Never opens the inspector from anywhere in this view.
- **Timeline view** (`timeline_view.py`) — Gantt-style horizontal bars by date range, grouped into per-project swimlanes (added 2026-07-19, see below). Bar position = `start_at`→`due_at`; bar fill = progress (now purely status-derived, see below). Drag to reschedule, drag an edge to resize (already snapped to whole-day increments live, not just on release — see `../STRESS_TEST_2026-07-17.md`, this one didn't have the calendar's snap-on-release bug). Persistence fixed 2026-07-18, see below. Day and Week zoom only — Month zoom was added and removed the same day (2026-07-20), see below.
- **Board (Kanban) view** — see `boards.md` for an important correction — this is a *different, separate* implementation from the general "board object" feature also described there, which is coded but unreachable. Persistence fixed 2026-07-18, see below. Card fields (priority/due date/project/tags) are now user-toggleable per the 2026-07-19 rework, see below.

## Removed 2026-07-19 — Smart list view

The old Smart list view (sidebar of saved filters: Today, Upcoming, All Open, High Priority, Waiting, Completed, Archived; rows with checkbox/title/project chip/priority/due date/progress bar/tags) was removed from the Tasks module entirely, along with `TaskRow`, `TaskListView`, and the old `TaskFilterBar`. Its role split in two:

- **"Today" and "Overdue"** moved to the Dashboard module, which is now strictly those two sections (Pinned and Upcoming were also dropped from Dashboard in the same pass — see `dashboard.md`).
- **The remaining five saved filters** (Upcoming, All Open, High Priority, Waiting, Completed, Archived) became `TaskTableFilterBar`, a chip bar embedded directly above the Table view (`table_view.py::SMART_FILTERS`), single-select, defaulting to "All Open".

Table is now the default Tasks view (was Smart); the view switcher is `["table", "timeline", "board"]`. The quick-add row (token syntax unchanged) moved from inside the old Smart view onto `TasksView` itself, above the view switcher, so it's available regardless of which view is active.

## Quick-add token syntax

Inline input at the top of any task view (`features/shared/create.py` is the shared parser used by both Dashboard and Tasks):

- `!1`–`!4` → priority (urgent → low)
- `@today` / `@tomorrow` / `@next-week` → due date
- `#project-name` → assign to project (creates the project if it doesn't exist)
- `>tag` → add tag
- plain text → title

## Checklist and subtasks

- **Checklist** (`widgets/checklist_editor.py`) — inline expandable list of checkbox + text rows inside the task inspector. Add/remove/toggle/reorder, persisted to `checklist.json`.
- **Subtasks** (`subtask_tree.py`) — objects with `parent_id` pointing at the task, shown nested/indented with expand-collapse. Completing all subtasks does not auto-complete the parent — they're independent objects.

## Task detail (inspector sidebar)

Opens on click from most views (see `../plans/tasks-ux-rework.md`, deleted 2026-08-11, for the per-view click-to-open rules that were still being finalized). Shows: title, status dropdown, priority dropdown, due/start date pickers, project selector, tags (multi-select autocomplete), progress slider, markdown description, checklist editor, linked objects section, backlinks, activity history. Shared with every other object type — see `tags-and-linking.md`.

## Timeline view reworked 2026-07-19 — project swimlanes

Requested: rows grouped by project, a project spanning multiple rows if its own tasks overlap in time, and tasks from different projects never sharing a row. Previously every task was one flat row in whatever order `set_objects` happened to receive them — no project grouping at all.

`TimelineCanvas._assign_swimlanes()` groups tasks by `parent_id`, then bin-packs each project's tasks into the minimum number of rows using the same interval-packing algorithm the calendar uses for overlapping events — extracted to a shared `core/utils/interval_packing.py` (`pack_intervals`) rather than duplicated, since it's the identical problem (assign the lowest free lane among concurrently-active intervals) applied to a different axis: horizontal columns within a calendar day vs. vertical rows within a project's swimlane. Project groups are sorted by title and stacked vertically, each getting its own contiguous row range — structurally, two different projects' tasks cannot land on the same row, since `row_offset` only ever increases between groups. A 92px left gutter shows each project's name, vertically centered across however many rows that project needed. Tasks with no project land in a trailing "(No project)" group. Two tests cover this (`TestTaskTimelineSwimlanes` in `desktop/tests/test_views.py`): overlapping same-project tasks land on different rows, and two different projects' row ranges never overlap.

## Timeline view fixed 2026-07-20 — zoom toolbar no longer scrolls away, resize hit target widened

**Zoom buttons scrolling out of view.** `TimelineView` was itself a `QScrollArea` whose single scrolled `container` widget held both the Day/Week/Month toolbar and the canvas in one `QVBoxLayout`. At Day zoom the canvas gets very wide (`day_width=80`, vs. 8–24 at Week/Month — `setMinimumWidth()` can reach several thousand px for a normal date range), so scrolling right to see later dates scrolled the toolbar off-screen along with it. Restructured so `TimelineView` is a plain `QWidget`: the zoom toolbar is a fixed row in its own top-level layout, and only `self._canvas` lives inside a (new, inner) `QScrollArea`. Verified with real geometry — after switching to Day zoom and scrolling the inner scroll area's horizontal bar to its maximum, the Day button's `mapToGlobal()` position is provably unchanged. Two regression tests in `desktop/tests/test_views.py::TestTimelineToolbar`.

**Resize "doesn't work" complaint.** First pass widened `HANDLE_WIDTH` from 6px to 10px and added grip marks (below) after an exact-pixel `QTest` drag reproduced no failure at any zoom level on a multi-day task — that wasn't the real bug. Follow-up report narrowed it: **resizing from the right just moves the bar; only for single-day (no explicit `start_at`) tasks; the left edge works.** Two real, distinct bugs, both specific to that case:

1. **Right-resize only ever wrote `due_at`.** A task with no explicit `start_at` has both `_bar_rect` (paint) and `mousePressEvent` fall back to using `due_at` as the display start. Growing `due_at` via a right-drag never touched `start_at` — so on the very next repaint, the still-unset `start_at` re-resolved to that same, just-moved `due_at`, and both edges of the bar walked forward together. Visually indistinguishable from a move, even though only `due_at` was actually being written. Left-resize never showed this because it writes `start_at` explicitly on the very first drag, which permanently escapes the fallback from then on — exactly matching "left works, right doesn't, only on first-touch single-day tasks." Fixed by freezing `start_at` to its resolved value the instant *any* resize drag begins, in `mousePressEvent`.
2. **Hit-test ambiguity on narrow bars.** A single-day bar at Month zoom is only 8px wide — narrower than the 20px combined width of both resize handles (10px each). `_hit_test` checked the left handle unconditionally first, so *any* click anywhere on such a bar — including right at its right edge — always resolved to `resize_left`, which then silently no-oped (its own guard rejects moving `start_at` past `due_at`). Fixed by splitting bars narrower than the combined handle width at their visual midpoint instead of a fixed handle-check order, so which half was actually clicked determines the mode.

Re-verified with real `QTest` press/move/release drags targeting single-day, no-`start_at` tasks specifically (the case that exposed both bugs) at all three zoom levels, plus a check that ordinary multi-day resizing is unaffected. Two permanent regression tests in `desktop/tests/test_views.py::TestTimelineResizeRightSingleDayTask`. The earlier grip-mark/wider-handle change (still in place) remains a real usability improvement but wasn't the actual bug.

## Timeline reworked 2026-07-20 — Week/Month zoom scaling

**The ask:** "rework the scaling of the month and week timeline things." Confirmed with the user: the actual problems were gridline/label clutter and too-short a time horizon at Month zoom, and the fix should widen Month zoom's default window and switch Week/Month zoom to week-boundary-only gridlines and labels (Day zoom keeps per-day granularity).

Previously every zoom level shared the identical default date window (`today-7`..`today+30`, ~37 days) and only changed `day_width` (80/24/8px). So "Month zoom" never actually showed more time than Week zoom — it just crushed the same five-ish weeks into 8px-wide day columns, and the header additionally tried to print a date number in *every* one of those 8px columns, which overlapped into an unreadable smear.

Two changes, in `TimelineCanvas`:

- **Per-zoom default window** (`_ZOOM_WINDOW_DAYS`): Day keeps the original ~37-day window (precise near-term editing is the point of Day zoom). Week widens to ~74 days. Month widens to ~180 days (roughly six months), which is what "Month zoom" should mean — a broad overview, not the same few weeks at smaller pixels. Still extended further if any task falls outside the default window, same as before.
- **Week-boundary-only gridlines and labels** (`_grid_line_day_indices()`): Day zoom still marks every day. Week and Month zoom now both mark only Mondays — one vertical gridline and one header label per week, format `"%b %d"` (e.g. "Jul 06") rather than a bare day number, since a wider window can span multiple months where a bare "06" is ambiguous. This replaced the old logic where Week zoom already labeled Mondays only but still drew a *gridline* for every day, and Month zoom labeled (and gridlined) every single day.

Bar rendering itself is unaffected — `_bar_rect`'s day-level math didn't change, so task positions/widths are still exact regardless of zoom; only how densely the grid/header paint at each zoom changed. Verified headlessly across all three zoom levels (window span, gridline-index list, and a real repaint with no exceptions) plus four permanent regression tests in `desktop/tests/test_views.py::TestTimelineZoomScaling`.

**Corrected same day, two more changes requested after seeing this land:**

- **Week zoom reverted to per-day gridlines/labels.** The first pass moved Week zoom to week-boundary-only marks alongside Month zoom, but Week zoom's whole point is showing days as the actual interval unit — so `_grid_line_day_indices()` now only collapses to week-boundary-only for Month zoom; Week (and Day) mark every day. Week zoom's per-day label is a bare day number (`"06"`, 24px/day doesn't have room for more), with the month spelled out (`"Jul 06"`) only at a week boundary or the 1st of a month, so crossing a month boundary is never ambiguous.
- **Month zoom hides tasks shorter than a week** (`MONTH_MIN_DURATION_DAYS = 7`, inclusive of both start and due date). At Month zoom's now-much-wider window, a 1-2 day task is both illegible and mostly clutter. `_is_visible_for_zoom(obj)` returns `False` for short tasks only when `self._zoom == "month"` — Day and Week zoom still show everything. This is wired into every place that matters, not just the paint call: `_draw_bars` skips hidden tasks, `_hit_test` skips them too (so a hidden task can't still be dragged/resized just because it exists in `self._objects`), `_assign_swimlanes` only packs visible tasks into rows (recomputed on `set_zoom`, not just `set_objects`, so switching to Month zoom actually compacts the swimlanes instead of leaving blank rows where hidden tasks used to be), and `_compute_range`'s window-extension logic ignores hidden tasks (so a stray short task far in the future doesn't stretch Month zoom's scrollable width just to fit a bar nobody sees).

Six permanent regression tests: `TestTimelineZoomScaling` (updated) confirms Week zoom marks every day and only Month zoom collapses to week boundaries; `TestTimelineMonthZoomFiltersShortTasks` covers visibility at each zoom, the exact 7-day boundary, and that a hidden task is genuinely non-interactive (`_hit_test` returns no match), not just invisible.

**Superseded later the same day — see the section below.** Month zoom (and everything specific to it: `MONTH_MIN_DURATION_DAYS`, `_is_visible_for_zoom`, the wider default window, week-boundary-only gridlines) was removed outright per explicit follow-up request, and Week zoom's header was reworked into two rows. `TestTimelineMonthZoomFiltersShortTasks` no longer exists.

## Timeline reworked 2026-07-20 — Month zoom removed, Week zoom gets a two-row heading, overlap-prevention re-verified

Three changes requested together, all in `timeline_view.py`:

- **Month zoom removed entirely.** Its own history above (widened window, week-boundary gridlines, hiding short tasks) never earned its keep — even tuned, it stayed a squeezed, low-value view compared to just scrolling Week zoom, which is the reason given for removing it. `TimelineView` now has only two zoom buttons (Day, Week); `TimelineCanvas` lost `MONTH_MIN_DURATION_DAYS`, `_is_visible_for_zoom`, and every call site that checked it (`_draw_bars`, `_hit_test`, `_assign_swimlanes`, `_compute_range`), reverting those methods to their simpler pre-Month-zoom form. `_grid_line_day_indices()` collapsed to "every day, always" since Week zoom already marks every day and Month zoom (the only zoom that didn't) is gone.
- **Week zoom's header is now two rows.** Previously a single row where a Monday's label used `"%b %d"` (e.g. "Jul 06", ~6 characters) inside a single 24px-wide day column — the text overflowed past its own column and visually overlapped the following days' bare-number labels ("now they just overlap"). Split into: row 1, a `"Week NN"` heading (`date.isocalendar()[1]`) drawn once per week, positioned at that week's Monday and free to use the whole week's ~168px width without colliding with anything; row 2, a plain per-day number (`"%d"`), one per day, on its own row 20px below row 1 with a thin divider line between them, so it never visually competes with row 1 regardless of how wide "Week NN" renders. A leading partial week (when the visible range's first day isn't a Monday) still gets a heading via `_week_start_indices()` including day 0 explicitly.
- **Automatic multi-row layout for overlapping same-project tasks — re-verified, not new.** This already existed (`_assign_swimlanes`, shipped with project swimlanes on 2026-07-19): it bin-packs each project's own tasks into the minimum number of rows so none of that project's tasks visually overlap, independent of zoom. It was never actually broken, but wasn't previously covered by an explicit "does this actually prevent overlap, per zoom" test — added one (`TestTimelineNoOverlappingTasksInARow`), which caught an indexing bug in the *test's own* ad-hoc verification along the way: `TimelineCanvas.set_objects` filters `self._objects` down to tasks only (project objects are dropped), so a test that built `[project, task1, task2]` and then indexed `canvas._row_for(1)` / `canvas._row_for(2)` was silently checking the wrong (and for index 2, out-of-range) objects — real indices need to be resolved by object id against the already-filtered `canvas._objects`, not assumed from the original input list's position.

Twelve permanent regression tests replace the six from the superseded section above: `TestTimelineZoomScaling` (only Day/Week buttons exist, Week's window widens, both zooms mark every day), `TestTimelineWeekHeading` (week-start indices land on Mondays, a leading partial week still gets one, the ISO week number is correct, a real repaint doesn't raise), and `TestTimelineNoOverlappingTasksInARow` (different rows at both zoom levels, and the painted rectangles genuinely don't intersect — the check that caught the indexing bug above).

**Superseded within the hour — see the section below.** The rolling `_ZOOM_WINDOW_DAYS` (today-N..today+M) window design was replaced with calendar-aligned months, and a second header-overlap bug (distinct from the one described above) was found via a rendered screenshot and fixed.

## Timeline reworked 2026-07-20 (again) — calendar-month-aligned zoom, week-label clipping fix

**The ask:** "for day, to show only the month. The week shows 3 months. One increment for day and week should be consistent." Confirmed with the user: calendar-aligned months (not a rolling today±N window), and also asked to re-verify the same-project overlap-prevention claim from the section above, specifically for tasks with no project.

- **Calendar-aligned zoom windows.** `_ZOOM_WINDOW_DAYS` (a rolling `today-N..today+M` day-count pair per zoom) was replaced with `_ZOOM_MONTH_SPAN` and a new `_month_bounds(base, offset_months)` static helper (handles year rollover via `divmod`-style arithmetic, using `calendar.monthrange` for each month's last day). Day zoom shows exactly the current calendar month (`span=0`: just that month). Week zoom shows the previous, current, and next calendar month (`span=1`: one month back, one month forward) — three calendar months total. This makes "one increment" a literal, named unit (one calendar month) shared by both zooms, rather than the two independently-tuned day counts the previous rolling-window design used. Still extended further if any task falls outside the default window, same as before. Verified with real geometry: at a run on 2026-07-18, Day zoom's `_start`/`_end` matched July 1–31 exactly; Week zoom matched June 1–August 31 exactly.
- **Same-project overlap prevention — investigated at length, could not reproduce a bug in the algorithm itself.** Stress-tested with random realistic data (multiple projects, many overlapping same-project tasks, tasks with no project) at both zoom levels and found zero row collisions; specifically re-tested "no project" tasks (the case named in the follow-up report) with both staggered and identical date ranges, and rendered actual screenshots (`TimelineCanvas.grab()`) confirming 4–5 genuinely overlapping no-project tasks each land on their own visually-distinct row. The bin-packing logic (`_assign_swimlanes`) was not changed in this pass. **What the screenshot did catch, unrelated to row-packing:** the Week zoom header's leading partial-week label (see "Week zoom's header is now two rows" above) could visually overlap the *next* week's label when the visible range doesn't start on a Monday and the partial week is narrower than the "Week NN" text itself — plausibly what read as an "overlap" bug in the report, even though it was a header-label collision, not a task-row collision. Fixed by clipping each week label to a `QRectF` bounded by the next label's x-position (Qt's rect-based `drawText` clips by default, unlike the bare `(x, y)` point-based call used before) instead of letting it draw unbounded.

Three more permanent regression tests: `TestTimelineZoomScaling::test_day_zoom_shows_exactly_the_current_calendar_month` and `::test_week_zoom_shows_previous_current_and_next_month` assert the exact calendar-aligned boundaries by independently recomputing them with `calendar.monthrange`; `TestTimelineWeekHeading::test_leading_partial_week_label_is_clipped_not_overlapping` reproduces the narrow-partial-week geometry and asserts the available width for that label is strictly less than a full week's width and never negative.

## Table view fixed 2026-07-20 — single-click editing

**The ask:** editing a dropdown cell (status/priority/project) took a double-click to enter edit mode, then a second click to open the combo box's popup — three clicks to change one value — with a request for hover-to-reveal-arrow, click-to-edit-and-open instead.

First attempt used `QAbstractItemView.EditTrigger.CurrentChanged` on the theory that a click changing the current index is exactly that trigger. It looked correct in a headless test (calling `table.model().index()` directly and simulating one click opened the editor), but the user reported the real running app still needed two clicks — the first only selected the row/cell, the second opened the editor. The actual fix: edit triggers are now keyboard-only (`EditKeyPressed`/`AnyKeyPressed`), and `_table.clicked` is connected directly to `_table.edit`, so every completed click (press+release on a cell) explicitly forces that cell into edit mode — deterministic, not dependent on Qt's internal timing for when a trigger check happens relative to selection-on-press. `TaskTableDelegate.createEditor` schedules `QTimer.singleShot(0, combo.showPopup)` on every dropdown editor it creates, so the popup is already open by the time the editor becomes visible: one click now both opens and expands the dropdown. `TaskTableDelegate.paint()` was extended to draw a native down-arrow (`QStyle.PE_IndicatorArrowDown`) at the right edge of status/priority/project cells whenever `option.state` has `State_MouseOver` set, which requires `self._table.setMouseTracking(True)` (added) so Qt tracks per-cell hover without a button held. Verified with real `QTest.mouseClick`s on the table viewport (not raw model-index lookups) — including a click on a cell in a row that was never previously the current index, which is what exposed the first approach's real-world failure — confirming the editor opens on exactly one click every time; four regression tests in `desktop/tests/test_views.py::TestTaskTableSingleClickEdit`.

## Fixed 2026-07-20 — Timeline/smart-list right-click menu (status change, duplicate, delete) never persisted

**How this surfaced:** the user reported edits in the Timeline view "revert to a 0 state" on app restart. Drag-to-reschedule/-resize was re-verified end-to-end with the user's real data (a temp copy of their actual `~/CommandCenter/objects/`, loaded through the same `_default_command_center()` settings-driven path resolution the real app uses, not an explicit `base_path` shortcut) and persists correctly — that was a false lead. The real bug was `TasksView._on_task_context_action` in `widgets.py`: the handler behind the right-click menu shared by both the smart-list row *and* the Timeline bar (`self._timeline_view.context_action.connect(self._on_task_context_action)`). Its `duplicate`, `delete`, and `status:<value>` branches only mutated `self._task_list._all_objects` (a plain in-memory Python list) and called `set_objects()` to re-render — none of them ever called `FileRepository().write_object()` or `.delete_object()`. A status change, a duplicate, or a delete looked like it worked for the rest of the session (the in-memory list and every view reading from it were consistent) and silently reverted on the next restart, since nothing had actually reached disk. This is the exact same class of bug as the 2026-07-18 Kanban-drag/Timeline-drag fix described above — and, notably, `TimelineCanvas`'s own drag persistence (in this same file, `timeline_view.py`) and `TaskTableView`'s duplicate/delete (`table_view.py`) already followed the correct write-through pattern; only this one shared handler was missed when that fix was made.

`KanbanBoard._on_card_action` in `kanban_view.py` (see `boards.md`) had the identical bug in its own `duplicate`/`delete`/`status:` branches, independently of the Tasks-widgets handler — fixed the same way, same day, once the pattern was spotted.

Both fixes add the missing `FileRepository().write_object(...)` (duplicate, status) or `FileRepository().delete_object(object_id)` (delete, which soft-deletes via `deleted_at` — the established convention, matching `TaskTableView._delete_row`) at the point each action actually happens, and duplicate now also copies `start_at`/`parent_id` onto the new object (previously dropped, an unrelated completeness gap noticed while touching this code).

**Testing note:** both handlers construct `FileRepository()` with no arguments, by design (see `_default_command_center()`'s docstring in `core/filerepo/repository.py` — this is what lets changing Settings → General → Folder path move every ad-hoc call site at once, not just whichever repository instance `MainWindow` happens to hold). Verifying the fix therefore requires monkeypatching `_default_command_center()` itself to point at a temp directory (see `TestContextMenuActionsPersist` in `desktop/tests/test_interactions.py`) rather than passing an explicit `base_path`, since an explicit `base_path` on a locally-constructed repository wouldn't exercise the same no-args resolution the real handler code uses — passing one would have hidden this exact bug. Five regression tests cover status/duplicate/delete for both Timeline (via `TasksView._on_task_context_action`) and Kanban (via `KanbanBoard._on_card_action`), each verified by re-reading from a brand-new `FileRepository` instance (simulating a real app restart) rather than checking in-memory state.

## Reworked 2026-07-19 — Smart view removed, progress derived from status, Table view is a real Notion-style database, tag management

Five changes requested together:

- **Smart view removed, split between Dashboard and Table view's new filter bar.** See "Removed 2026-07-19 — Smart list view" above.
- **Progress is now purely derived from status, everywhere.** `core/models/object.py::progress_for_status()` maps `active→0%, in_progress→50%, waiting→90%, done/archived→100%`. Every status-change call site (`TaskTableModel.setData`, `TasksView._on_task_context_action`, `KanbanBoard._move_card`/`_on_card_action`, `SubtaskTree._toggle_subtask`, the inspector's `_save`) now sets `obj.progress` from this function instead of leaving it independently editable. The inspector's Progress section (a slider) was deleted outright — not just hidden. The Table view's Progress column is now display-only, rendered as a colored pill showing the derived percentage; there's no percentage-input editor anywhere in the app anymore.
- **Table view pill rendering.** `TaskTableDelegate` now custom-paints status/priority/project (and the derived progress) as rounded colored pills with formatted labels ("In Progress", not `in_progress`) instead of plain enum text, reusing the app's existing `core/design/tokens.py` semantic colors so pills stay legible in light and dark mode. Due dates render via `core/utils/date_utils.py::relative_date_label()` ("Today"/"Tomorrow"/"Mon"/"In 2w"/absolute "Jul 25" once relative phrasing stops being useful). Columns can now be drag-reordered directly (`header.setSectionsMovable(True)`, `sectionMoved` persists through the same `_apply_column_order` path the right-click menu's move-left/right already used), in addition to the existing right-click reorder.
- **Kanban card fields are now customizable.** A "⚙ Card fields" button in a new toolbar row above the board columns opens a checkable menu (priority/due date/project/tags — project is off by default, the other three on), persisted to `settings.json` under `kanban_card_fields`. `_KanbanCard` only renders whichever fields are enabled.
- **Tag management:** Settings → Tags gained a "Merge into…" action per row (picks another existing tag, rewrites every affected object's `tags` list, deletes the source tag) and a usage-count column. Rename and merge now both write through to the actual object files via `FileRepository` (not just the SQLite tag cache) — previously `rename_tag` only touched the DB cache, which is itself rebuilt from each object's own `tags` field on reindex, so a rename would silently revert on the next reindex/restart (same bug class as the 2026-07-18 Kanban/Timeline persistence fixes). Tag-name autocomplete (`features/tasks/tag_autocomplete.py`, sourced from `features/shared/tag_names.py`'s process-wide cache of every tag currently in use, refreshed on every data reload) is now wired into both the inspector's tag input and the Table view's Tags cell editor.

See `dashboard.md` for the Dashboard side of the Smart-view split, `boards.md` for the Kanban card-fields detail, and `tags-and-linking.md` for the tag-manager rework.
