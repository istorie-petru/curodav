# Feature: Calendar

**Code:** `desktop/src/features/calendar/widgets.py`, `desktop/src/core/recurrence.py`
**Status:** Views/drag/multi-calendar/overlap-layout/recurrence implemented; external (CalDAV) lists are not (see below) — see also [`calendar-rework-history.md`](calendar-rework-history.md) for the feature-parity decisions made along the way and [`../STRESS_TEST_2026-07-17.md`](../STRESS_TEST_2026-07-17.md) for how the earlier state was verified

## Views

Switched via a segmented control in the toolbar:

- **Month grid** — event chips (colored by calendar) and task indicators (left border) per day. Click a day for an agenda side panel. Drag a chip to reschedule to a different day. Pan across empty days to create a new event.
- **Week grid** — 7-column × 24-hour time grid, with a vertical hairline between each day column (added 2026-07-19 — previously columns had no visible separator beyond the header labels). Events as positioned blocks (height = duration). Drag to move (horizontal = day, vertical = time); drag an edge to resize, snapping live to 15-minute increments (fixed 2026-07-19 — previously the block resized smoothly under the cursor and only snapped once, on release, so what you saw while dragging wasn't quite what got saved). All-day events shown in a strip above the grid.
- **Day grid** — same as week, single column.
- **Agenda list** — chronological list of upcoming events and due tasks, grouped by day, next 30 days.

**Fixed 2026-07-18 — drag-to-move and drag-to-resize in the week/day grid now actually persist.** Three compounding bugs, all in `_EventBlock`/`CalendarView` (`calendar/widgets.py`): (1) `_on_block_time_changed` used `datetime.now(timezone.utc)` with `timezone` never imported in the file — every single move or resize crashed with a `NameError` the moment you released the mouse, silently (Qt logs it, nothing visible in the UI), before any save was attempted. (2) Even past that, the handler only mutated the in-memory `Object` and re-rendered — no `FileRepository.write_object()` call existed at all. (3) The resize case specifically changes an event's `end_at`, which lives in `Object.details` (a free-form dict for type-specific fields) — and `FileRepository.write_object`/`read_object` never serialized `details` in the first place, so it round-tripped to `{}` on every read regardless. Fixed all three: added the missing import, added the write call, and `details` is now persisted as one JSON blob field on `object.json` (`core/filerepo/repository.py`) — same fix that incidentally also makes daily notes' `is_daily`/`daily_date` flags persist correctly (moot now — see `window-and-menu.md`, the Notes module and its daily-note integration were removed 2026-07-19). Verified by driving the actual `_EventBlock` widget through a resize and a move and reading the result back off disk.

**Fixed 2026-07-19 — overlapping events in the week/day grid no longer hide each other.** Every timed event used to render at the day column's full width regardless of what else was scheduled at the same time, so two overlapping events landed directly on top of each other — whichever was created second completely obscured the first, with nothing in the UI hinting there was a second event underneath. `_pack_overlaps()` (module-level function, `calendar/widgets.py`) now buckets a day's events into overlap clusters and greedily assigns each a lane (Google-Calendar-style column packing); both `WeekGrid` and `DayGrid` divide the available width by each cluster's lane count instead of always using the full width. Covered by a dedicated test (`test_overlapping_events_get_separate_columns`) in addition to the manual verification.

## Multi-calendar

Events belong to a named, color-coded calendar. Each has a visibility toggle (per-device, persisted locally). A legend panel lists calendars. **Not implemented:** external CalDAV calendar subscriptions (connecting to a remote server like Nextcloud/Radicale as an additional selectable list) — this is a real, substantial protocol-level feature, scoped separately in [`../plans/calendar-and-tasks-rework.md`](../plans/calendar-and-tasks-rework.md) §5 (deleted 2026-08-11), not attempted yet.

## Recurrence — implemented 2026-07-19

Previously verified broken (2026-07-17): `recurrence` was a real field on the model/schema with no parsing or expansion anywhere, and no UI to set it at all — the inspector had no event-specific fields whatsoever, contrary to what this doc used to claim (see "Event detail" below for the correction). Built as requested — a "schedule list": a weekly- or daily-repeating task/event between two dates, with specific dates excepted (e.g. a class timetable skipping a holiday).

- **`core/recurrence.py`** — `RecurrenceRule` (freq: daily/weekly, interval, weekdays, until-date or occurrence-count, exception dates), a purpose-built subset rather than full RFC 5545 (no BYMONTH/BYSETPOS/etc. — nothing in the app needs them). Serializes to an RRULE-*shaped* string (`FREQ=WEEKLY;BYDAY=MO,WE,FR;UNTIL=2026-12-31;EXDATE=2026-08-15`) stored in `Object.details["recurrence"]`, parse errors return `None` rather than raising (a hand-edited or corrupt value degrades to "not recurring", doesn't crash the calendar). `expand_occurrences(rule, dtstart, window_start, window_end)` generates occurrence dates for a window, with a hard cap so an unbounded rule can't hang the UI. 21 tests in `desktop/tests/test_recurrence.py`.
- **`expand_recurring_objects(objects, window_start, window_end)`** — the integration point every calendar view (Month/Week/Day/Agenda) calls before matching objects to day cells. Returns the original list plus one synthetic copy per additional occurrence (same id as the master — clicking any occurrence opens/edits the master event, per the "master is the source of truth, occurrences are computed, never stored" principle the architecture doc has always specified). `start_at`/`details["end_at"]` are shifted by the same day-delta as the occurrence, preserving time-of-day and duration.
- **UI (`widgets/inspector.py`)** — a "Repeats" checkbox reveals frequency (Daily/Weekly), interval, weekday checkboxes (weekly only), an end condition (never / until date / after N times), and exception-date management (an "Except due date" button adds whatever's currently in the Due date field above; "Clear" resets). This is the *only* place a rule is edited — every view just reads and expands it.
- **Bug fixed along the way:** saving any event through the inspector was silently stripping its time-of-day. The Start Date field is a date-only `QDateEdit`, and `_save()` unconditionally overwrote `start_at` with just the new date — recurrence made this impossible to ignore (an anchor time of midnight makes a "9am standup" schedule useless), so `_save()` now preserves the existing time-of-day when only the date changed.

Verified end-to-end: set a repeat rule through the real `InspectorPanel` widget, saved, read back off disk, expanded, and confirmed occurrences render in `MonthGrid`/`WeekGrid` with correct dates and shifted times — not just the underlying engine in isolation.

**Still not built:** per-instance exceptions that *modify* rather than remove an occurrence (e.g. "move next Tuesday's class to 2pm" without affecting the rest of the series) — only whole-occurrence removal (exception *dates*) exists. See [`../plans/expansion-deferred.md`](../plans/expansion-deferred.md).

## Event detail (inspector sidebar)

**Correction, 2026-07-19:** this used to claim the inspector had "date/time pickers, all-day toggle, calendar selector, location, meeting URL, reminders" for events — checked while building the recurrence UI, and none of that exists. The inspector is entirely generic across every object type: title, status, priority, a date-only due-date picker, a date-only start-date picker (time-of-day can only be set by dragging an event in the week/day grid, not typed in directly), a progress slider, tags, markdown description, checklist, linked objects, backlinks — plus, as of today, the recurrence section described above. There is no event-specific location/meeting-URL/calendar-selector/reminders UI anywhere in the app despite those fields existing on `EventDetails` in the model.
