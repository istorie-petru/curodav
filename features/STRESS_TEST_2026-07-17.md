# Stress test report — 2026-07-17

**Method:** ran the existing `desktop/tests/` suite headless (`QT_QPA_PLATFORM=offscreen`), then wrote additional scripts exercising the data layer, quick-add parsing, search, boards, projects, exports, attachments, and WebDAV at higher volume and with more adversarial input than the shipped tests cover, then booted the real `MainWindow` headless and drove it through real widgets (not mocks). This file records what actually happened, graded by how confident the result is: **Verified working**, **Verified broken**, or **Verified but with caveats**.

The short version: the data core (file tree + HLC merge + SQLite cache) is solid under load. Several features documented as "Implemented" in this folder are not reachable, not persisted, or silently no-op. Those are corrected below and need fixing in the corresponding `features/*.md` files (flagged inline) or in the code.

## Existing test suite

All 73 tests in `desktop/tests/` pass headless, unchanged. This was already true before this pass; it's a real baseline, not padding — but it's a happy-path suite (simple ids like `"test-1"`, no adversarial input, no multi-run persistence checks), which is exactly the gap this stress pass targeted.

## Verified working, holds up under load

- **FileRepository** (`core/filerepo/repository.py`) — wrote/read 3000 objects (~0.1–0.3s for the batch), `iter_objects()` survived 50 corrupted `object.json` files with no crash (skips them silently), SQLite `rebuild_from_path` handled the same 3000 objects without issue.
- **HLC** (`core/sync/hlc.py`) — 5000 rapid `send()` calls stayed strictly monotonic and unique; 70,000 same-millisecond sends didn't trip the `0 <= counter <= 0xFFFF` assertion.
- **HLC conflict merge on read** (`FileRepository._resolve_conflicts`) — a synthetic Syncthing conflict file with a newer title and an older status merged correctly per-field (newer wins, older is discarded, conflict file is deleted after merge). This is the one piece of logic the architecture doc calls "the code that can silently destroy data," and it held up.
- **Quick-add token parsing** (`features/shared/create.py`) — priority/date/tag tokens parse correctly, tags actually persist to disk and survive a read round-trip (a stale docstring in that file says tags are "not yet persisted" — they are; the comment is wrong, not the code). Out-of-range priority tokens (`!5`, `!0`) are correctly ignored. Re-using the same `#project-x` token doesn't create duplicate projects. Long unicode titles are handled fine.
- **Kanban drag-and-drop, within Tasks** (`features/tasks/kanban_view.py`) — this is the actually-reachable kanban view (see "Verified broken" below for the *other* one); it's a real `QDrag`/`dropEvent` implementation that updates status and persists.
- **Wikilinks and backlinks** (`features/notes/widgets.py`) — `[[Title]]` parsing on save creates real `mentions` links via `db.create_link`, and backlinks query the correct index.
- **Project derived progress** (`features/projects/widgets.py`) — computed as `done/total` from real child-task counts, not stored.
- **Attachments store** (`core/attachments/store.py`) — content-addressed dedup works (two different filenames with identical bytes land in the same `sha256` dir); delete removes the data.
- **App boot** — `MainWindow` builds and every top-level module (Dashboard, Tasks, Calendar, Notes, Roadmap, Search, Settings, Projects) navigates without exception, headless. Quick-add through the real dashboard widget works end-to-end.

## Verified broken

- **Global search / command palette is non-functional.** `core/db/database.py` defines `_upsert_fts()` to populate the `objects_fts` FTS5 table, but **nothing in the codebase calls it** — grepping the whole file finds exactly one occurrence of the name (its own definition). The FTS5 index is created by the schema but never populated. Confirmed empirically: `SearchEngine.search("BAC")` against real data returns `[]` every time, for every query, because the join (`JOIN objects o ON o.id = objects_fts.rowid`) has nothing to match against. Worse, even if it were populated, inserting a UUID string as `rowid` into this particular FTS5 table configuration raises `sqlite3.OperationalError: datatype mismatch` (reproduced directly against the schema in isolation) — so the fix isn't just "call `_upsert_fts`," the rowid strategy itself needs to change (e.g. a separate integer surrogate key, or `content_rowid` mapped properly). Separately, a bare `"` in a query crashes `SearchEngine.search()` with an unhandled `OperationalError: unterminated string` — the FTS5 query builder doesn't escape user input. → **`features/search.md` needs a correction**, this is not "Implemented."
- **The general Boards/Kanban module (`features/boards/widgets.py::BoardsView`) is unreachable.** It's fully coded — real drag-and-drop, card CRUD, custom-pipeline columns, cover images — but it is never imported or instantiated anywhere outside its own file. `MainWindow`'s module list is `Dashboard, Tasks, Calendar, Notes, Roadmap, Search, Settings` plus `Projects`; there is no "Boards" entry and no way to create a `type=board` object from the UI. What users can actually reach is a *different*, simpler kanban view inside Tasks (`features/tasks/kanban_view.py`, fixed 4 columns: Todo/In Progress/Waiting/Done) — that one works (see above). → **`features/boards.md` conflates the two** and needs to be split: the Tasks kanban view is real, the general custom-board feature is dead code with no entry point.
- **JSON import doesn't persist.** `MainWindow._on_import()` (`app.py`) reads a JSON dump via `import_json()` and appends the results to the in-memory `self._all_objects` list, then refreshes the UI — it never calls `file_repo.write_object()`. Imported objects appear for the current session and are silently gone on next launch, since they were never written to `~/CommandCenter/objects/`.
- **Obsidian vault import is unreachable *and* not idempotent.** `import_obsidian_vault()` exists in `core/export/impex.py` but `_on_import` only ever calls `import_json` — there's no UI path that calls the Obsidian importer at all. Independent of that, it generates object ids via `hash(str(rel)) % 10**15`, and Python's string `hash()` is randomized per-process by default (`PYTHONHASHSEED`) — re-running the same import in a fresh process produces a different id for the same file every time (verified: same file, two processes, two different ids), so even if it were wired up, re-importing a vault would create duplicates instead of updating.
- **Embedded WebDAV server does not start.** `WebDavServer.start()` raises `TypeError: 'NoneType' object is not reversible` inside `wsgidav` initialization when given the app's config dict (the `middleware_stack: None` key appears to be the trigger). Reproduced directly by starting a real server against a temp directory and making an HTTP request — it never came up, so the request failed. This is a basic smoke-test-level break, not an edge case. → **`features/sync-and-webdav.md` needs correcting** for the WebDAV half; the Syncthing REST client half is fine (see below). **Fixed 2026-07-18** — see `features/sync-and-webdav.md`'s WebDAV section for the two bugs (the `middleware_stack: None` here, plus a second one this same report didn't catch: `WsgiDAVApp` has no `serve_forever()`, so the original code would have failed differently even with bug 1 fixed) and the live-request verification.

## Verified but with caveats

- **Atomic writes are not implemented**, despite `plans/systems/architecture.md`'s risk table claiming "atomic writes (write temp file + rename) in filerepo" as a mitigation. `_write_json()` in `repository.py` is a direct `path.write_text()` — no temp file, no `os.replace()`. A crash or power loss mid-write, or two processes writing the same object concurrently, can leave a torn/corrupt `object.json`. This doesn't show up in normal single-threaded testing (which is presumably why it read as fine), but the mitigation I wrote into the architecture doc describes code that doesn't exist. **This needs fixing in `plans/systems/architecture.md`** (correct the risk table) and ideally in `repository.py` (actually add the temp+rename).
- **`FileRepository()` is instantiated bare (no `base_path`) in several UI call sites** — `widgets/object_card.py` (duplicate/delete), `features/boards/widgets.py` (duplicate/save/delete/drop), `features/tasks/table_view.py` (inline edit/duplicate/delete) — instead of reusing the app's configured repository instance. Every one of these defaults to `~/CommandCenter`. Today this is harmless because the app always uses that same default everywhere (see next point), but it's a latent bug: if a different data folder is ever wired in, these specific actions (kanban drag, card duplicate/delete, table inline edit) would silently read/write the wrong folder while the rest of the app used the right one.
- **Settings → General → "Folder path" is a stub.** It's a real, working text field with a folder browser, and it saves to `settings.json` — but nothing reads it back into `FileRepository`'s `base_path`. `app.py` always constructs `FileRepository()` with no argument, i.e. always `~/CommandCenter`, regardless of what's configured. The only place the setting is used at all is to compute the "Data size" label in Settings → About. Changing it does not move where the app actually stores data.
- **`export_json` silently drops tags.** The exported dict's field list doesn't include `tags` at all — round-tripping export→import loses every object's tags. Everything else round-trips correctly (title, status, priority, dates).
- **Recurrence (RRULE) is a stored field with no consumer.** `task_details.recurrence` / `event_details.recurrence` exist in the model and schema, but there is no RRULE parsing or expansion anywhere in `features/calendar/widgets.py` or elsewhere in the codebase — confirmed by grep, not just absence of a UI control. The calendar shows events on their stored date only; nothing expands a recurring master event into occurrences. → **`features/calendar.md`'s recurrence section needs correcting** — it currently describes this as built.
- **Quick-add with only tokens and no plain text** produces a task titled literally `"!1 @today"` instead of an empty/placeholder title — a real, minor bug (the title-building code falls back to the raw input string when `title_parts` ends up empty).
- **Syncthing REST client is safe against "not running"** at its actual UI call site (`SyncthingSettingsTab._check_connection` pings first, then wraps `.status()`/`.connections()` in `try/except`) — but the `SyncthingClient` methods themselves (`status()`, `connections()`, `folder_status()`, etc.) have no internal guard and will raise `URLError`/`OSError` if called directly without going through that pattern. Not a bug today (there's exactly one call site and it's careful), but fragile if a second caller is added without copying the same guard.

## What this means for the docs

`features/search.md`, `features/boards.md`, `features/sync-and-webdav.md` (WebDAV section), `features/calendar.md` (recurrence section), and `features/data-and-attachments.md` (import/export section) currently overstate what's built and need correction — they were written from the original spec (`plans/systems/decisions-log.md`) and the presence of substantial, well-written source files, not from actually exercising the features. `plans/systems/architecture.md`'s risk table also needs its atomic-write claim corrected. None of the other feature docs turned up discrepancies at this level.
