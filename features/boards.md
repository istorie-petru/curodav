# Feature: Kanban boards

**Code:** `desktop/src/features/tasks/kanban_view.py` (reachable), `desktop/src/features/boards/widgets.py` (orphaned — see below)
**Status:** Two different implementations exist; only one is reachable. See [`../STRESS_TEST_2026-07-17.md`](../STRESS_TEST_2026-07-17.md). Dead-space bug fixed 2026-07-20 (see below).

There are two separate kanban codebases in this repo, and the original version of this doc conflated them. They are not the same feature.

## What's actually reachable: Tasks → Kanban view

`features/tasks/kanban_view.py::KanbanBoard`. This is the Kanban option in the Tasks module's view switcher (Smart List / Table / Timeline / Kanban). Fixed 4 columns (Todo / In Progress / Waiting / Done), mapped to the task status vocabulary. **Verified working**: real Qt drag (`QDrag`/`dropEvent`), dropping a card changes `status` and persists via `FileRepository.write_object()`; "add card" per column. Right-click card menu offers status changes, edit, duplicate, delete — see the persistence fix directly below; the "offers" part was always true, whether those choices actually *stuck* past a restart was not, until 2026-07-20.

**Fixed 2026-07-20 — dead space between the column header and the first card.** A previous pass (2026-07-19, see `../plans/calendar-and-tasks-rework.md` item 4, deleted 2026-08-11) read `_KanbanColumn.__init__` end to end and couldn't find the cause, since nothing in the layout code obviously reserved blank space — no stretch item, no fixed-height spacer. The actual cause only showed up under real rendering: a plain `QLabel`'s default vertical `QSizePolicy` is `Preferred`, which *permits* it to grow past its own `sizeHint()`. The column's `QVBoxLayout` (header → card list → add-input) had no explicit stretch item, so when a column had few/no cards, Qt handed all the unused vertical space to whichever item's policy allowed growing — the header was the only candidate (the add-input `QLineEdit` is already `Fixed`), so it silently absorbed the entire gap: confirmed by inspecting real geometry, the header's `sizeHint()` was 17px but its actual allocated height was up to 549px in an empty column. Fixed by pinning the header to `QSizePolicy.Policy.Fixed` vertically and adding an explicit `layout.addStretch(1)` between the card list and the add-input, so leftover space goes where it visually belongs (above the add-card box) instead of as an invisible gap above the cards. Verified with real `.show()`/`.resize()`/`processEvents()` geometry inspection (header height dropped to the correct ~17-21px in every column) and two permanent regression tests in `desktop/tests/test_views.py::TestKanbanGeometry`.

**Fixed 2026-07-20 — card context menu (status change, duplicate, delete) never persisted.** `KanbanBoard._on_card_action` handled all three right-click actions by mutating `self._all_objects` (in-memory) and calling `_refresh()` — none of them called `FileRepository().write_object()`/`.delete_object()`. Only the *drag-and-drop* status change (`_move_card`, a separate method, already correct) actually reached disk; the context-menu route to the exact same status change did not. A status change, duplicate, or delete via the right-click menu looked like it worked for the rest of the session and reverted on the next restart. This is the same bug, independently present, as `TasksView._on_task_context_action` in `../features/tasks/widgets.py` (shared by the smart-list row and the Timeline bar) — see `tasks.md` for the full writeup and how it was found (starting from a user report that Timeline edits "revert to a 0 state" on restart). Fixed the same way: `write_object()` after mutating status or building the duplicate, `delete_object()` (soft-delete via `deleted_at`) instead of just filtering the in-memory list. Two regression tests in `desktop/tests/test_interactions.py::TestContextMenuActionsPersist` cover Kanban's status-change and duplicate/delete paths, each verified by re-reading from a brand-new `FileRepository` instance rather than checking in-memory state.

## What's coded but unreachable: the general `board` object type

`features/boards/widgets.py::BoardsView` — a more general implementation where each board is its own object (`type=board`) with custom columns defined in `board_details.columns` (`[{id, name, object_status}]`), meant to support arbitrary pipelines like "Idea → Draft → Review → Published" alongside the fixed task board. The code is real and reasonably complete (drag-and-drop, card CRUD, cover-image display), but **it is never imported or instantiated anywhere outside its own file** — grepping the app finds no navigation entry, no "New board" action, and no route to it. A user cannot currently create or view a custom-pipeline board through the UI. If this is wanted, the missing piece is wiring: a sidebar/nav entry, a board-creation flow, and routing `type=board` objects to `BoardsView`.

## Added 2026-07-19 — customizable card fields ("frontmatter")

The Tasks Kanban view's cards previously always showed a fixed set of fields (priority, due date, tags — no way to add or remove any). A "⚙ Card fields" button in a new toolbar row above the columns (`KanbanBoard`, `kanban_view.py`) opens a checkable menu of `CARD_FIELDS` (priority, due date, project, tags — project is off by default, the other three on), persisted to `settings.json` under `kanban_card_fields`. `_KanbanCard` now takes a `visible_fields` set and only renders whichever are enabled; a `project` field was added to cards for the first time (resolves `parent_id` to a title via `KanbanBoard.project_title()`, same pattern as the Table view's Project column). Due dates on cards now render relatively (`relative_date_label()`) instead of the raw ISO string, matching the Table view.

Progress is no longer a separately-tracked field anywhere, including here — a status change (drag between columns, or the right-click "Move to" menu) now also sets `obj.progress` via `progress_for_status()` alongside the status write, so it stays in sync with the Table view/inspector's derived progress. See `tasks.md` for the full 2026-07-19 rework.

## Known gaps

- Per-view settings for column visibility (Tasks Kanban view's fixed 4 columns) and cover-image handling (always/never/only-if-present) still aren't exposed in the UI — previously tracked in `../plans/tasks-ux-rework.md` (deleted 2026-08-11, superseded by the webapp rework). Card *field* customization (this doc, above) is done; column customization is not.
