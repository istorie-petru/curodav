# Projects, Tasks, and Work Allocation

Projects are not a separate organizational primitive from labels. A project is a user-created label with the Project behavior enabled. This gives the label a bounded period, defined by a start and end date, and a dedicated project view that aggregates the entities carrying that label. The label remains usable across the rest of the application, so a project can be combined with other labels such as `University`, `Historiography`, or `Important` without introducing a second hierarchy.

A project represents an outcome or area of work that exists over a period of time. Its dates describe the project's overall horizon, not the period during which every associated task must be worked on. A project such as `Conference XYZ`, running from August 11 to October 13, can contain tasks that have no independent start or due date. The project provides the context and deadline; the individual work is scheduled separately.

The existing task hierarchy should therefore be simplified by removing subtasks. A task is an independent unit of work that can optionally belong to one or more labels, including a project label. Tasks do not initially require start or due dates. They retain their status, title, description, estimated work, priority and other task-level metadata, while their actual working time is represented through work allocations.

A work allocation represents a planned amount of work on a task at a specific time. It is represented in the calendar as an Event linked to the task, but it is not a different kind of calendar object. The distinction comes from the relationship: an ordinary event represents something that happens, while an event linked through a work allocation represents time reserved to work on a task. A task may have any number of work allocations, allowing its estimated work to be distributed across multiple days and weeks.

For example, a task such as `Research` belonging to the `Conference XYZ` project might require three hours. It can initially exist without dates. The user can then allocate one hour on Monday and two hours on Thursday. The task retains an estimated workload of three hours, while its scheduled work is derived from its allocations. If an allocation is moved or resized, the scheduled amount changes accordingly. The task's derived schedule can therefore be calculated from its allocations rather than maintained as manually entered task dates.

The same work allocation can be manipulated directly from the project's scheduling view. An unscheduled task can be dragged into an available period, creating a calendar event for the allocated amount of time. Resizing that event changes the amount of work allocated to the task. The same task can be scheduled in multiple blocks across multiple weeks, and individual blocks can be moved, resized, split, or removed without creating duplicate tasks. The task remains one piece of work; its calendar allocations describe when that work is performed.

Task management should remain focused on managing the underlying work rather than scheduling it. The Tasks page can therefore provide a table or database-style view grouped by project label, allowing tasks belonging to each project to be viewed together. This provides the organizational structure needed for project work without introducing a separate task hierarchy. Tasks that do not belong to a project remain ordinary standalone tasks and continue to function as a simple to-do list.

Projects receive their own dedicated page in the main sidebar. The page initially displays current projects as cards rather than presenting them as another dense database table. Each card should contain meaningful live information such as the project name, date range, task progress, estimated workload, scheduled workload, remaining unscheduled work, and upcoming deadline. The project overview should make the current state of the user's projects understandable at a glance without requiring the user to open each one.

Opening a project provides two primary views. The first is a task-management view focused on the work belonging to that project. Tasks can be added quickly, edited, completed, filtered, and grouped without leaving the project. The project label is automatically applied to newly created tasks, while other labels remain independently assignable. This view is the project's work-management interface.

The second view is a project-specific week calendar. It provides the direct scheduling interface for the project's tasks. Unscheduled tasks are presented in a dedicated area above the calendar, with each item showing its project context, task name, and remaining estimated work. These tasks can be dragged onto the calendar to create work allocations, then moved, resized, or split directly on the calendar. The project schedule therefore becomes the place where planning and time allocation happen, rather than adding task-scheduling controls throughout the global Calendar interface.

The project week calendar should still display ordinary calendar events because they determine whether time is actually available. Project work allocations should be visually prominent, while unrelated events should be visually subdued. Busy periods can use reduced opacity or a restrained hashed treatment to communicate that the time is occupied without making unrelated events compete with the project's work. The calendar therefore acts as a planning surface for the project while preserving enough surrounding context to make realistic scheduling possible.

The global Calendar remains focused on calendar management: viewing, creating, editing, moving, and organizing events. It should not be overloaded with project-specific task allocation controls. Similarly, the global Tasks page remains focused on managing tasks and their metadata. The Project page is the deliberate meeting point between the two systems: it provides the context of a project, the work belonging to it, and the calendar space in which that work can be scheduled.

This model removes the need for the previous task subtasks. A task does not become structurally different because it requires several work sessions. Multiple sessions are simply multiple work allocations. A project does not need to contain a hierarchy of increasingly specialized task objects; it provides a bounded context in which independent tasks can be created, managed, and scheduled. The resulting model is deliberately small: labels provide organization, project-enabled labels provide bounded work contexts, tasks describe work, and calendar events represent actual time, with work allocations connecting the two.
