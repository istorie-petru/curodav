## 0. What changed from v1 of this plan

Your last message moves this further than "collapse Project/Space into Label" — it also removes the *storage* role that CalDAV/CardDAV collections (`calendars`, `task_lists`, `addressbooks`, `project_groups`) currently play. Restating your intent back, precisely, so the schema below is built on the right reading:

1. **A label is not an entity with a lifecycle.** No create/delete workflow, no cascading-delete concerns. It's a name that tasks/events/contacts point at. "Deleting" a label just means nothing points at it anymore. Any color/icon/behavior config for a label is a thin, optional dictionary keyed by the label's name — not a row other tables hold a hard foreign key into.
2. **Tasks/events/contacts become one universal pool per type**, not partitioned by "which calendar/list/addressbook it lives in." Creating a task never requires picking a list. Organization is 100% by label.
3. **WebDAV/CalDAV/CardDAV formatting is still respected per-object** (a task is still representable as a valid VTODO, a contact as a valid vCard) but no longer dictates the app's internal structure. The one remaining place collections matter is a *new*, opt-in feature: Settings lets you define a named list as "everything carrying label X," which the app materializes into a real Radicale collection and publishes a syncable URL for — read-only at minimum, so e.g. a phone calendar app can subscribe to just your `University` events without seeing everything.
4. **Labels are globally unique.** One `University` label, referenced by name from anywhere — not re-created per context.
5. **`contacts.category` is purged**, and so is anything else that duplicates what a label now does.

This means the base sync question needs one explicit assumption stated up front (§1) rather than left implicit, since it's the one piece of this with real data-safety weight.

## 1. Base pool storage — resolved 2026-08-06

The app runs as a single central server instance; the web interface is the only access path, and data doesn't leave the server unless a List (§3 Phase 6) is deliberately published. There's no multi-device-via-Radicale problem to solve for the base pool — it isn't syncing copies to multiple local clients, it's one server everyone hits over the web. So the base pool (`tasks`/`events`/`contacts`) is **plain SQL, full stop** — no invisible default Radicale collection, no `href`/`etag` against any collection for base rows. "Respect WebDAV formatting" (§0.3) now means only: fields stay shaped so a row *can* be serialized to a valid VEVENT/VTODO/VCARD on demand — for the export feature and for §3 Phase 6's Lists — not that base storage round-trips through Radicale at all. Radicale is now used for exactly one thing in this app: materializing and serving published Lists.

## 2. Schema shape (supersedes v1's `labels` table design)

- **`tasks`, `events`, `contacts`** — unchanged in spirit (still the WebDAV-mappable rows: title, dates, raw_ics/raw_vcard, etc.), but drop `calendar_path`/`list_path`/`addressbook_path`/`*_project_uid`/`group_uid`/`tags_json`/`category` entirely. Every row keeps only what a valid VEVENT/VTODO/VCARD needs plus its `uid`/`href`/`etag` against the *one invisible default collection* from §1.
- **`object_labels(object_type, object_id, label_name)`** — the only join table. `label_name` is the natural key (globally unique text, not a surrogate id) — reinforces that a label isn't a row you reference by FK-with-delete-semantics, it's a string a query filters on.
- **`label_config(label_name PRIMARY KEY, color, icon, description, parent_name, generate_space, enabled_modules_json, dashboard_preset_json)`** — optional, sparse config. A label with zero rows here still fully works (default color, no space page, appears in "manage labels" purely because `object_labels` mentions it). This table has no delete-cascade relationship to anything; a row here going stale (unused) is harmless and doesn't need cleanup.
- **`published_lists(id, name, entity_type, label_filter_json, radicale_collection_path, sync_direction, last_materialized_at)`** — new, from §3 Phase 6. One row per Settings-created List. `label_filter_json` holds a boolean expression over label names (AND/OR/NOT, e.g. `University AND NOT Archived`), not just a single label — confirmed 2026-08-06. `sync_direction` starts as an enum with only `read_only` implemented; the column exists now so a future two-way mode doesn't need a migration.
- **Dropped entirely:** `calendars`, `task_lists`, `addressbooks` (as user/app-facing multi-collection concepts — replaced by the one invisible default + N published Lists), `project_groups`, `projects`, `tags`, `tag_groups`.
- **Unaffected:** `habits`/`habit_entries` (per your instruction — stay as their own local-only pair, gain `object_labels` rows the same way tasks do, nothing else changes), `schedule_classes`/`schedule_holidays`/`schedule_settings`, `grades`/`databases`/`database_columns`/`database_rows`, `dashboard_widgets` (its `space_uid`/`project_uid` FK becomes a plain `label_name` filter, nullable for Home).

## 3a. Known open risk — `project_label_for`'s heuristic (flagged 2026-08-06, unresolved)

`schedule_classes`/`habits`/`databases` each derive "the project" as *whichever attached label isn't a Space, picked alphabetically if more than one qualifies* (`db.py::project_label_for`). This is deliberate — no separate "this is THE project" field, consistent with §0.1 — but it's a real heuristic, not a guarantee: a class/habit/database carrying two ordinary (non-Space) labels at once will silently have the wrong one treated as "the project" (whichever sorts first). Low risk at today's usage patterns (most of these objects carry at most one non-Space label), but worth knowing before it's relied on somewhere higher-stakes. No action taken yet — flagging for a decision (accept as-is / require a UI warning when >1 non-Space label is present / something else) rather than guessing.

## 3. Phases

### Phase 1 — Universal pool: drop collection partitioning
Drop `calendar_path`/`list_path`/`addressbook_path`/`href`/`etag`/`raw_ics`/`raw_vcard` from `tasks`/`events`/`contacts` as *storage* — they become plain SQL rows with no Radicale relationship at all (per §1). Keep enough structure (title/dates/location/etc., and a serializer function) that a row can still be turned into a valid VEVENT/VTODO/VCARD on demand for export and for §3 Phase 6's Lists, but nothing about base storage depends on Radicale anymore — `caldav_bridge.py`/`sync.py`'s role shrinks from "the source of truth" to "the thing Phase 6 calls when materializing a published List." Every prior *collection membership* (which calendar/list/addressbook something was in) becomes a label: e.g. if "Work Calendar" was a real calendar, everything in it gets tagged with a new `Work Calendar` label. Add `object_labels`. Acceptance: every task/event/contact still has a working "export as .ics/.vcf" path (proves the serializer stayed correct even though nothing writes to Radicale for base storage anymore); querying `object_labels` for an old collection's derived label name returns exactly what used to be in that collection; `webapp/tests` no longer depend on `FakeBridge` for any base CRUD test, only for Phase 6's List-publishing tests.

## 4. Testing & migration safety

Unchanged principle from v1: every phase gets `webapp/tests/test_phaseN_*.py` (seed → act → assert user-observable result + DB/bridge round-trip); full suite green at the end of every phase; Phase 1's collection-consolidation migration is the highest-risk step in this version of the plan (re-homing every object's Radicale `href`) — needs a dry-run mode and a pre-migration snapshot, same as v1's label backfill did, before it touches real data.

**Standing rule (confirmed 2026-08-06):** test cleanup is part of every phase, not a separate pass. Whenever a phase deletes a table/router/feature, it deletes or rewrites the tests that exercised it in the same phase — no orphaned test files, no tests asserting behavior of code that no longer exists, no accumulating cruft to clean up "later." Phase 1 already did this (deleted `calendars`/`task_lists`/`addressbooks` router tests alongside the routers). Phase 2 onward keeps the same discipline for `tags`/`tag_groups`/`project_groups`/`projects` and their tests.
